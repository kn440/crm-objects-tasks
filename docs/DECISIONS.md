# Решения и допущения

## 1. Согласованные решения

Уточнены у заказчика в чате до начала работы.

1. **Смена исполнителя.** Постановщик может сменить исполнителя в любом статусе, кроме «Принята» и «Отменена». Задача возвращается в «Новая», новый исполнитель сам берёт её в работу. В историю пишется «Исполнитель изменён: А → Б». Постановщик может указать причину смены; если она указана, она тоже сохраняется в истории.
2. **Удаление.** Задачу можно удалить, только пока она в статусе «Новая» и её ни разу не брали в работу. Дальше — только отмена. Объект можно удалить, только если в нём нет задач.
   - Решающее условие — история, а не текущий статус: если задача хоть раз переходила «В работу», удалить её нельзя, даже если после смены исполнителя она снова «Новая». Иначе через смену исполнителя можно было бы удалить задачу вместе с историей работы.
3. **Редактирование.** Название и описание постановщик меняет в любом статусе, кроме «Принята» и «Отменена». Изменение текста не меняет статус и не сбрасывает исполнителя. Объект задачи меняется только в статусе «Новая». Исполнитель ничего не редактирует, только меняет статус. **Правки текста в историю не пишутся** — в карточке видна только дата последнего изменения («Изменена»). Кто и что именно поменял в тексте, сейчас не отслеживается; это закрывает пункт «Полный аудит» в разделе 4.
4. **Отмена и ошибочная приёмка.** Добавлен статус «Отменена»: ставит постановщик из любого незавершённого статуса, комментарий обязателен, статус окончательный. Добавлен переход «Принята → На доработке» с обязательным комментарием (обнаружен брак).

## 2. Принятые допущения

Решила сама там, где ТЗ не даёт однозначного ответа.

### Бизнес-правила

- **Исполнитель обязателен при создании задачи** — иначе задача зависнет в «Новая», брать её в работу некому. Назначить можно только пользователя с ролью «Исполнитель».
- **Принимать, возвращать и отменять может любой постановщик**, не только автор задачи: по ТЗ постановщик «видит всё», а постановщиков может быть несколько. В тестовых данных постановщик один (по ТЗ требуется минимум один); правило обеспечивается базой: функция смены статуса проверяет роль пользователя, а не автора задачи.
- **Комментарий** обязателен при возврате на доработку и при отмене, в остальных переходах — по желанию.
- **После смены исполнителя прежний исполнитель теряет доступ к задаче** — по правилу «исполнитель видит только свои задачи».
- **Исполнитель видит имена только тех, кто связан с его задачами** (авторов и участников истории), а не список всех сотрудников. Почта пользователей в приложении не хранится и не показывается.
- В карточке задачи показан **счётчик возвратов на доработку** — считается из истории.
- В «Моих задачах» по умолчанию **только активные задачи**, завершённые («Принята», «Отменена») — на отдельной вкладке.

### Технические решения

- **Роль хранится в таблице `profiles`**, а не в метаданных пользователя: метаданные пользователь может изменить сам. Профили через API изменить нельзя никому, роли назначаются в базе.
- **Статус, автора и даты ставит база**, а не клиент: даже если отправить запрос со `status = 'accepted'` или чужим автором, база откажет.
- **Смена статуса и исполнителя — только через функции базы** (`change_task_status`, `reassign_task`). Прямое изменение этих полей закрыто правами на колонки и дополнительно триггером.
- **Одновременные действия** обрабатываются внутри транзакции базы: функция блокирует строку задачи (`select … for update`) и только потом проверяет текущий статус. Второе действие получает отказ, если статус уже изменился. Проверка истории перед удалением тоже выполняется в базе (триггер `tasks_before_delete`), а не в интерфейсе.
- **На чужую задачу исполнитель получает ответ «Задача не найдена»**, а не «нет прав»: так нельзя узнать, существует ли задача.

## 3. История и контроль данных

- Все события по всем задачам пишутся в **одну таблицу `task_history`**: создание задачи, каждая смена статуса (с комментарием) и смена исполнителя. Кто, когда, из какого статуса в какой.
- Пишут туда только триггеры и функции базы. Пользователи могут только читать историю задач, которые им видны: постановщик — всех, исполнитель — своих. Изменить или удалить записи истории не может никто.
- **Единственное исключение:** удаление задачи вместе с записью о её создании допускается, только если задача ни разу не переходила в работу. Все остальные события истории сохраняются и не могут быть удалены пользователями. Задачи с историей только отменяются, и отмена остаётся в истории.
- **Не записываются:** создание, правка и удаление объектов; правки названия и описания задачи (по согласованию).
- Всё перечисленное проверено автоматически: `supabase/tests/security_check.sql` (44 проверки в базе) и `npm run security-check` (31 проверка через API).

## 4. Возможности развития

Всё из ТЗ сделано. Ниже — то, что сознательно оставлено за рамками тестового.

- **Сроки выполнения** — сознательно не делала: на стройке не для каждой задачи удобно назначать срок. Если понадобятся — необязательное поле срока и логика определения просрочки; «просрочена» — отдельная отметка, а не статус.
- **Общий журнал событий** для постановщика. Данные и правила доступа уже готовы; для реализации потребуется отдельный экран с лентой событий и фильтрацией по объектам, задачам и сотрудникам.
- **Аналитика по истории:** доля задач, принятых с первого раза, число возвратов, время от взятия в работу до приёмки — по объектам и исполнителям.
- **Фотоотчёты:** фото к сдаче работы и к замечаниям при возврате.
- **Полный аудит:** отдельная таблица `audit_log`, куда триггеры пишут создание, правку и удаление объектов и задач (кто, когда, что было до и после). Тогда будут видны удаления и правки текста задачи.
- Архив завершённых задач и сданных объектов.
- Отказ исполнителя от задачи.
- Уведомления (почта, мессенджер) о новых задачах и возвратах.
- Экран управления пользователями и ролями (сейчас — через Supabase).
- Автотесты интерфейса.
