# Объекты и задачи — мини-CRM для стройки

Постановщик ставит задачи по объектам (стройкам), исполнители берут их в работу и сдают на проверку. Права доступа и правила смены статусов проверяет база данных (Supabase / Postgres), а не только интерфейс.

**Стек:** React 18 + TypeScript (Vite), Mantine, Supabase (Postgres, Auth, RLS).

## Тестовые доступы

| Роль | Email | Пароль |
| --- | --- | --- |
| Постановщик | manager@test.ru | manager1 |
| Исполнитель 1 | worker1@test.ru | worker11 |
| Исполнитель 2 | worker2@test.ru | worker21 |

Пароли намеренно простые и годятся только для демонстрации. В рабочей системе — политика сложных паролей Supabase Auth и учётные записи, которые выдаёт администратор.


## Запуск

### 1. Supabase

1. Создать проект на [supabase.com](https://supabase.com).
2. **Authentication → Sign In / Providers**: выключить *Allow new users to sign up* и *Confirm email*.
3. **Authentication → Users → Add user → Create new user** (с *Auto Confirm User*):
   `manager@test.ru`, `worker1@test.ru`, `worker2@test.ru`.
4. **SQL Editor**: по очереди выполнить три файла из `supabase/migrations/`, затем `supabase/seed.sql`.
   Или через CLI: `supabase link --project-ref <ref>` и `supabase db push`, затем `seed.sql` в SQL Editor.
5. Проверка: выполнить `supabase/tests/security_check.sql` в SQL Editor — во всех строках `passed = true`.
   Скрипт ничего не меняет, каждая попытка откатывается.

### 2. Приложение

```bash
cp .env.example .env     # вписать VITE_SUPABASE_URL и VITE_SUPABASE_PUBLISHABLE_KEY
npm install
npm run dev              # http://localhost:5173
```

Значения берутся в Supabase → **Connect** (или **Project Settings → API Keys**). Во фронтенд идёт только публичный ключ (publishable / anon); секретный ключ (service_role / secret) проекту не нужен и нигде не используется.

### 3. Проверка защиты через API

В `.env` дописать пароли тестовых пользователей и выполнить:

```bash
npm run security-check
```

Скрипт входит под каждой ролью с публичным ключом и пытается обойти правила напрямую через API: прочитать чужие задачи, сменить статус в обход действий, подделать историю, присвоить себе роль постановщика, зарегистрироваться. Временные данные, которые он создаёт, удаляются.

### 4. Деплой на Vercel

Импортировать репозиторий, указать переменные `VITE_SUPABASE_URL` и `VITE_SUPABASE_PUBLISHABLE_KEY`. `vercel.json` уже настроен для клиентской маршрутизации.
В Supabase → **Authentication → URL Configuration** указать адрес сайта в *Site URL*.

## Как устроена защита

| Требование | Как сделано |
| --- | --- |
| Права закрыты на уровне базы | RLS на всех таблицах; для `anon` нет ни одной политики |
| Исполнитель не видит и не меняет чужое | `tasks`: видны только строки с `assignee_id = auth.uid()`; объекты — только с его задачами; править задачи может только постановщик |
| Запрещённый переход не пройдёт | Колонки `status` и `assignee_id` закрыты на запись правами на колонки. Менять их можно только функциями `change_task_status` и `reassign_task`, которые проверяют матрицу переходов, роль, назначенного исполнителя и комментарий. Второй рубеж — триггер, который отклоняет смену статуса мимо этих функций |
| Историю нельзя подделать | На `task_history` у клиентов только `SELECT`. Записи создают триггеры и функции; автор записи — `auth.uid()`, а не значение из запроса |
| Роль нельзя присвоить себе | Роль хранится в `profiles`, которую через API изменить нельзя (не в `user_metadata`) |
| Регистрация закрыта | Отключена в настройках Auth; пользователи создаются администратором |
| Секреты не утекают | Во фронте только публичный ключ, `.env` в `.gitignore` |

Одновременные действия (два постановщика нажали «Принять» и «Вернуть») не перезаписывают друг друга: функция блокирует строку задачи (`select … for update`), второй запрос увидит новый статус и получит отказ.

## Статусы

| Из | В | Кто | Комментарий |
| --- | --- | --- | --- |
| — | Новая | постановщик, при создании | — |
| Новая | В работе | назначенный исполнитель | — |
| В работе | На проверке | назначенный исполнитель | — |
| На проверке | Принята | постановщик | — |
| На проверке | На доработке | постановщик | обязателен |
| На доработке | В работе | назначенный исполнитель | — |
| Принята | На доработке | постановщик | обязателен (обнаружен брак) |
| Новая / В работе / На проверке / На доработке | Отменена | постановщик | обязателен |
| любой незавершённый | Новая (смена исполнителя) | постановщик | пишется автоматически |

Последние три строки добавлены по согласованию с заказчиком — подробнее в [docs/DECISIONS.md](docs/DECISIONS.md).

## Локальная проверка миграций без Supabase

```bash
createdb crm
psql -d crm -f supabase/tests/local_supabase_stub.sql
for f in supabase/migrations/*.sql supabase/seed.sql; do psql -d crm -v ON_ERROR_STOP=1 -f "$f"; done
psql -d crm -f supabase/tests/security_check.sql
```
